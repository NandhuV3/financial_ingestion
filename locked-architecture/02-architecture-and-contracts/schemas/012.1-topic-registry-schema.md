# Topic- Registry Schema

Status: LOCKED

# 1. Purpose

The Topic Registry Schema defines the canonical structure of every Topic stored in the Topic Registry.

This document defines:

- the Topic data model
- required fields
- optional fields
- lifecycle fields
- relationship fields
- versioning fields
- validation rules

This document does **not** define:

- Topic governance
- Topic admission
- Topic Assignment behavior
- Topic Evolution behavior

Those responsibilities belong to their respective specifications.

# 3. Topic Schema

```ts
type TopicLifecycleState =
    | "proposed"
    | "provisional"
    | "active"
    | "deprecated"
    | "merged"
    | "retired";

interface TopicRegistryEntry {

    /*
     * Stable platform identifier.
     * Never changes.
     */
    topic_id: string;

    /*
     * Canonical business concept.
     */
    canonical_name: string;

    /*
     * Human-readable business definition.
     */
    definition: string;

    /*
     * Alternative names that map to this Topic.
     */
    aliases: string[];

    /*
     * Lifecycle state.
     */
    lifecycle_state: TopicLifecycleState;

    /*
     * Registry version where this Topic first appeared.
     */
    created_registry_version: number;

    /*
     * Registry version of the latest modification.
     */
    updated_registry_version: number;

    /*
     * Parent Topic.
     * Optional.
     */
    parent_topic_id?: string;

    /*
     * Child Topics.
     */
    child_topic_ids: string[];

    /*
     * Used only when lifecycle_state == "merged".
     */
    merged_into_topic_id?: string;

    /*
     * Used only when lifecycle_state == "deprecated".
     */
    deprecated_reason?: string;

    /*
     * Embedding model version used when generating semantic
     * representations.
     */
    embedding_version?: string;

    /*
     * Example Theme titles that represent this Topic.
     *
     * Used only for governance,
     * not by Topic Assignment.
     */
    examples: string[];

    created_at: string;

    updated_at: string;
}
```

---

# 4. Required Fields

Every Topic must contain:

- topic_id
- canonical_name
- definition
- aliases
- lifecycle_state
- created_registry_version
- updated_registry_version
- child_topic_ids
- examples
- created_at
- updated_at

---

# 5. Optional Fields

Optional fields include:

- parent_topic_id
- merged_into_topic_id
- deprecated_reason
- embedding_version

These fields appear only when applicable.

---

# 6. Field Definitions

## topic_id

Purpose:

Stable platform identifier.

Properties:

- immutable
- globally unique
- never reused
- never reassigned

Example

```
topic:cloud-computing
```

---

## canonical_name

Purpose:

Official Topic name.

Example

```
Cloud Computing
```

---

## definition

Purpose:

Business definition of the Topic.

Example

```
Products and services providing on-demand computing,
storage, networking, and software capabilities over
internet-based infrastructure.
```

---

## aliases

Purpose:

Alternative names.

Example

```
Cloud

Cloud Platform

Cloud Infrastructure
```

Aliases never create new Topics.

---

## lifecycle_state

Valid values

```
proposed

provisional

active

deprecated

merged

retired
```

---

## created_registry_version

Registry version where this Topic first became available.

Example

```
5
```

---

## updated_registry_version

Most recent registry version affecting this Topic.

Example

```
9
```

---

## parent_topic_id

Optional hierarchical relationship.

Example

```
Cloud Computing

↓

Infrastructure
```

---

## child_topic_ids

Zero or more child Topics.

Example

```
Infrastructure

↓

Cloud Computing

↓

Cloud Storage

↓

Cloud Security
```

---

## merged_into_topic_id

Present only for merged Topics.

Example

```
AI Compute

↓

merged_into

Artificial Intelligence Infrastructure
```

---

## deprecated_reason

Human-readable explanation.

Example

```
Merged into broader Topic.
```

---

## embedding_version

Semantic embedding version used by governance.

Example

```
text-embedding-3-large-v2
```

Topic Assignment must never depend on this field.

---

## examples

Example Theme titles that belong to this Topic.

Purpose:

Governance only.

These examples help maintain Topic consistency.

They are not training data.

They are not assignment rules.

Example

```
Cloud Infrastructure Expansion

Azure Capacity Investment

Regional Datacenter Growth
```

---

# 7. Validation Rules

Every Topic must satisfy:

- topic_id is unique.
- canonical_name is unique.
- definition is non-empty.
- aliases contain no duplicates.
- aliases must not equal canonical_name.
- lifecycle_state must be valid.
- child_topic_ids must contain unique Topic IDs.
- parent_topic_id cannot equal topic_id.
- merged_into_topic_id cannot equal topic_id.
- created_registry_version <= updated_registry_version.

---

# 8. Relationship Rules

A Topic may have:

- zero parent
- one parent
- many children

Cycles are forbidden.

Example

```
A
↓
B
↓
C
↓
A
```

Invalid.

---

# 9. Registry Version Rules

Every Registry modification creates a new Registry version.

Existing Topic IDs never change.

Historical Registry versions are immutable.

Historical Topic definitions remain reproducible.

---

# 10. Historical Immutability

Once a Topic Assignment records

```
registry_version = 12
```

the assignment always refers to Registry Version 12.

Future Registry changes never rewrite historical assignments.

Historical artifacts remain reproducible forever.

# 12. Golden Rules

The Topic Registry Schema defines Topic structure only.

It does not define governance.

It does not define Topic Assignment.

It does not define Topic Evolution.

Every Topic has exactly one stable identifier.

Topic identifiers never change.

Registry versions never rewrite historical assignments.

Historical reproducibility is mandatory.

Topic Assignment consumes this schema.

Only Topic Registry Governance may modify it.
