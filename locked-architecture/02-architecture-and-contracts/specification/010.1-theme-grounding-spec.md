# Theme Grounding Specification

Version: 1.0
Status: LOCKED
Owner: Theme Grounding Layer

## Layer Contract Summary

Inputs

* Themes Execution Readiness Result

Outputs

* Theme Grounding Result

Primary Consumer

* Theme Input Boundary Layer

Execution Type

* Deterministic

---

# Purpose

Theme Grounding is the canonical deterministic grounding layer before the
first LLM.

It answers:

```text
What deterministic evidence package is available for Theme extraction?
```

Theme Grounding owns:

* grounding package construction
* canonical evidence packaging
* evidence ordering preservation
* grounding metadata
* grounding scope
* deterministic grounding context

It assembles the canonical grounding package that later becomes the source for
Theme Input Boundary construction.

Theme Grounding contains no intelligence.

It performs no business reasoning.

It performs no observation extraction.

It performs no LLM reasoning.

---

# Output Classification

Output Classification:

```text
Transient BuilderResult
```

Justification:

Theme Grounding assembles deterministic grounding information.

It performs no intelligence generation.

It performs no interpretation.

It performs no LLM reasoning.

It enables downstream Theme Input Boundary construction by packaging canonical
evidence in deterministic order.

The grounding package is consumed only by the immediately following Theme
Input Boundary builder.

It is inexpensive to reproduce from the Themes Execution Readiness Result.

It has no independent business or governance value outside execution flow.

Therefore Theme Grounding output is a Transient BuilderResult.

It is not a Platform Artifact.

It does not participate in the Artifact Framework.

It is not versioned, persisted, or addressed as an artifact.

Why this satisfies the Output Classification criteria:

* the output does not represent governed business knowledge
* the output is consumed only by Theme Input Boundary
* downstream lineage does not reference it as a Platform Artifact
* the output is not valuable independently of the immediately following
  builder
* operational execution details, if needed, belong to execution observability
  rather than the Artifact Framework

Grounding package fields are content-level grounding fields owned by this
specification.

---

# Input Boundary

Theme Grounding consumes only:

* Themes Execution Readiness Result

It must never consume:

* Filing Artifact
* Evidence Identity directly
* Extraction output
* Normalization output
* raw SEC filings

All upstream validation has already completed.

Themes Execution Readiness is the only approved upstream input.

This preserves deterministic layer ownership and prevents upstream boundary
leakage.

---

# Output Principle

Theme Grounding produces exactly one canonical Grounding Package for one
Themes Execution Readiness Result.

This Grounding Package becomes the only approved source for Theme Input
Boundary construction.

No downstream layer may reconstruct or redefine the Grounding Package.

---

# Canonical Grounding Principle

Grounding is established exactly once.

Theme Grounding is the only layer that assembles the canonical Grounding
Package for Theme extraction.

Every downstream Theme extraction must use the canonical Grounding Package.

No downstream layer may:

* reconstruct grounding
* change evidence ordering
* add hidden evidence
* remove canonical evidence
* redefine grounding metadata
* substitute prompt delivery structure for grounding identity

This principle prevents prompt-boundary ambiguity and preserves one
authoritative grounding package for Themes.

---

# Ownership Boundary

Theme Grounding owns:

* canonical grounding package
* evidence selection scope
* deterministic grounding metadata
* evidence ordering preservation
* grounding completeness
* deterministic grounding context

Theme Grounding does not own:

* readiness evaluation
* prompt construction
* prompt variables
* LLM inputs
* Theme extraction
* Topic Assignment
* Topic Evolution
* Structured Intelligence
* Company Knowledge
* Quarter Change
* Business Signals
* trust intelligence
* Quarter Understanding
* Investor Intelligence
* investor conclusions or recommendations
* artifact persistence or lifecycle mechanics

Themes Quality owns readiness evaluation.

Theme Grounding consumes Themes Execution Readiness and produces the canonical
Grounding Package.

Theme Grounding must not reopen Evidence Identity to assemble grounding.

Theme Input Boundary owns prompt exposure boundaries.

Themes owns filing-scoped observation extraction.

Downstream layers consume grounding through the approved Theme Input Boundary
and Themes flow.

Theme Grounding never:

* constructs prompts

# Theme Grounding Content

The Theme Grounding builder returns:

```typescript
BuilderResult<ThemeGroundingContent>
```

```typescript
type ThemeGroundingContent = {
  readiness_result_id: string;
  filing_id: string;
  filing_hash: string;
  grounding_version: string;
  grounding_scope: GroundingScope;
  ordered_evidence: GroundingEvidenceEntry[];
  section_hierarchy: GroundingSection[];
  grounding_metadata: GroundingMetadata;
};

type GroundingScope = {
  evidence_entry_count: number;
  section_names: string[];
};

type GroundingEvidenceEntry = {
  evidence_ref: string;
  evidence_hash: string;
  section_name: string;
  paragraph_index: number;
  paragraph_text: string;
};

type GroundingSection = {
  section_name: string;
  evidence_refs: string[];
};

type GroundingMetadata = {
  source_readiness_result_id: string;
  source_evidence_identity_artifact_id: string;
  generated_from_readiness_status: "ready";
};
```

`ThemeGroundingContent` is the canonical execution result for the deterministic
grounding package.

It is not a prompt.

It is not an LLM input.

It is not a Theme.

It is not a Topic.

It is not business understanding.

It is not investor interpretation.

---

# Grounding Package Contract

The canonical Grounding Package contains only deterministic information.

It includes:

* source readiness result
* filing identity
* evidence references
* ordered evidence
* section hierarchy
* grounding metadata
* grounding version

It must not include:

* prompts
* prompt variables
* LLM instructions
* observations
* Themes
* Topics
* business meaning
* interpretation
* investor reasoning

Grounding package construction must preserve canonical evidence ordering from
the validated evidence carried by the approved upstream readiness source.

The package may expose paragraph text only as deterministic grounding context
associated with canonical evidence references.

Paragraph text must not become a replacement grounding identity.

---

# Canonical Evidence Source

Theme Grounding uses only the validated canonical evidence carried by Themes
Execution Readiness.

Every grounding evidence reference must resolve through the upstream
readiness source to canonical Evidence Identity.

Theme Grounding must not reopen Evidence Identity to resolve, reconstruct, or
replace evidence.

Grounding may not use the following as grounding identities:

* raw filing text
* raw SEC HTML
* normalized section paths
* processed section paths
* chunk IDs
* extraction identifiers
* temporary identifiers
* prompt-generated identifiers
* inferred identifiers
* Theme IDs
* evidence hashes substituted for references
* Platform Artifact IDs as grounding identities
* Artifact Framework lineage entries as grounding identities

Source text may be included in the Grounding Package as context. Source text
must not be returned in place of a canonical evidence reference.

---

# Grounding Ordering

Grounding ordering preserves canonical evidence ordering.

Ordering must be deterministic for every execution.

Ordering must not depend on:

* filesystem enumeration
* object key order
* asynchronous completion order
* prompt delivery order
* LLM output order
* downstream artifact order

Grounding ordering must preserve:

* source section order
* paragraph order within each section
* canonical evidence reference association
* section hierarchy

Downstream layers may expose bounded portions of the package through Theme
Input Boundary, but they must not redefine canonical grounding order.

---

# Grounding Metadata

Grounding metadata identifies the deterministic source and scope of the
Grounding Package.

Minimum metadata includes:

* source readiness result id
* source evidence identity artifact id
* filing id
* filing hash
* grounding version
* evidence entry count
* section names
* readiness status used for grounding

Grounding metadata must not include:

* prompt templates
* prompt variables
* model identifiers
* LLM output
* Theme candidates
* observations
* business interpretation

---

# Grounding Completeness

Theme Grounding must include every canonical evidence entry within the
approved grounding scope.

For the default scope, the grounding package includes the full validated
evidence set carried by the ready Themes Execution Readiness Result.

If future filing-type policies define bounded grounding scopes, those scopes
must be deterministic, contract-owned, and replayable.

Grounding completeness must not be determined by prompt size, model context
limits, or LLM behavior.

Theme Input Boundary may decide what portion of the Grounding Package is
exposed to the Themes prompt.

Theme Grounding owns the canonical package.

Theme Input Boundary owns exposure.

---

The Theme Grounding builder owns:

* grounding package assembly
* deterministic ordering
* grounding validation
* grounding result construction

The builder returns:

```typescript
BuilderResult<ThemeGroundingContent>
```

The builder must never:

* summarize evidence
* infer business meaning
* extract Themes
* assign Topics

* create evidence identities
* persist Platform Artifacts directly
* assign artifact IDs

The standard builder lifecycle, output handling, and failure behavior are

# Validation

Theme Grounding validates that the Grounding Package is complete,
deterministic, ordered, and correctly scoped to the source Themes Execution
Readiness Result.

Validation must verify:

* grounding completeness
* evidence ordering preserved
* reference integrity
* readiness source consistency
* deterministic assembly
* replay consistency
* grounding metadata completeness
* grounding scope consistency
* section hierarchy consistency
* filing identity consistency
* filing hash consistency
* ordered evidence derives from readiness `validated_evidence`
* every `evidence_ref` resolves to approved upstream evidence
* no prompt fields are present
* no Theme fields are present
* no Topic fields are present

Validation failures must stop grounding result creation.

Validators must not silently remove, rewrite, repair, or replace invalid
grounding entries.

Validation must not evaluate:

* Theme quality
* prompt quality
* business quality
* investor quality
* LLM behavior
* model behavior

Those responsibilities belong to downstream layers or other contracts.

---

# Replayability

Theme Grounding is deterministic.

For identical Themes Execution Readiness Result content and identical Theme
Grounding contract version:

```text
Identical Themes Execution Readiness Result
      ↓
Identical Theme Grounding Result
```

Theme Grounding generation must produce:

* identical grounding scope
* identical ordered evidence
* identical section hierarchy
* identical grounding metadata
* identical Theme Grounding content

Replayability must not depend on:

* prompts
* providers
* models
* LLM output
* mutable external state
* downstream artifacts
* filesystem enumeration order
* execution concurrency

Theme Grounding generation must be deterministic and must not use an LLM.

---

# Output Boundary

The output of Theme Grounding is consumed only by the Theme Input Boundary
layer.

Theme Grounding must not communicate directly with:

* Themes
* Topic Assignment
* Structured Intelligence
* Company Knowledge
* Business Signals
* Quarter Understanding
* Investor Intelligence

All downstream intelligence flows through Theme Input Boundary and Themes.

---

# Downstream Boundary

Theme Input Boundary consumes Theme Grounding.

Theme Input Boundary must never:

* reconstruct grounding
* reorder evidence
* redefine grounding scope
* add hidden evidence
* remove canonical evidence
* replace grounding metadata

Theme Grounding determines the canonical evidence package.

Theme Input Boundary determines what portion of that package is exposed to the
Themes prompt.

Themes begin where Theme Input Boundary ends.

---

# Future Compatibility

Theme Grounding is filing-type aware but remains deterministic.

Future filing categories may introduce new canonical sections, including:

```text
10-K
transcript
investor_presentation
other approved filing categories
```

Each filing-type policy may define deterministic grounding expectations for
the Grounding Package.

Future filing types must continue using:

* canonical readiness input
* canonical evidence references
* deterministic evidence ordering
* grounding metadata
* grounding scope
* replayable package construction

Adding a filing type must not change existing Theme Grounding outputs for
previously supported filing types.
