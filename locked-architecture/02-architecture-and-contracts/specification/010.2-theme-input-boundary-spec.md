# Theme Input Boundary Specification

Version: 1.0
Status: LOCKED
Owner: Theme Input Boundary Layer

## Layer Contract Summary

Inputs

* Theme Grounding Artifact

Outputs

* Theme Input Boundary Artifact

Primary Consumer

* Themes Layer

Execution Type

* Deterministic

---

# Purpose

Theme Input Boundary is the canonical deterministic visibility layer before
the first LLM.

It answers:

```text
What deterministic information is the Themes Builder allowed to consume?
```

Theme Input Boundary owns:

* LLM-visible evidence selection
* deterministic input payload
* input visibility rules
* exposure boundaries
* canonical input contract
* deterministic input metadata

It defines what information the Themes Builder is permitted to see.

Theme Input Boundary contains no intelligence.

It performs no reasoning.

It performs no prompt generation.

It performs no LLM invocation.

It performs no Theme extraction.

---

# Platform Object Classification

Theme Input Boundary is a Platform Foundation Artifact.

Reason:

Theme Input Boundary constructs the deterministic LLM-visible input contract.

It performs no reasoning.

It performs no prompt generation.

It performs no intelligence.

It enables downstream Theme extraction by defining what deterministic
grounding information is visible to the Themes layer.

Artifact Framework owns:

* artifact identity
* framework metadata
* framework lineage
* artifact versioning
* persistence
* current pointer management
* archive and history
* framework-level artifact hashes

The Theme Input Boundary content contract does not own those mechanics.

Input package fields are content-level visibility fields owned by this
specification.

---

# Input Boundary

Theme Input Boundary consumes only:

* Theme Grounding Artifact

It must never consume:

* Themes Execution Readiness
* Evidence Identity
* Filing Artifact
* raw SEC filings
* Extraction output
* Normalization output

Theme Grounding is the only approved upstream input.

This preserves deterministic layer ownership and prevents upstream boundary
leakage.

---

# Output Principle

Theme Input Boundary produces exactly one canonical Theme Input package for
one Theme Grounding Artifact.

The Themes Builder must consume only this package.

No downstream layer may redefine the visible input.

---

# Visibility Principle

Theme Grounding defines everything that exists.

Theme Input Boundary defines what is visible.

The Themes Builder consumes only what Theme Input Boundary exposes.

This separation is permanent.

---

# Ownership Boundary

Theme Input Boundary owns:

* visible evidence payload
* visible metadata
* deterministic input structure
* exposure rules
* visibility filtering
* canonical input package

Theme Input Boundary does not own:

* Grounding Package construction
* prompt templates
* prompt variables
* prompt wording
* prompt construction
* LLM invocation
* Theme extraction
* Topic Assignment
* Topic Evolution
* Structured Intelligence
* Company Knowledge
* Quarter Change
* Business Signals
* trust intelligence
* Quarter Understanding
* Investor Intelligence
* investor conclusions or recommendations
* artifact persistence or lifecycle mechanics

Theme Grounding owns the canonical Grounding Package.

Theme Input Boundary consumes Theme Grounding and produces the canonical
visible input package.

Themes owns filing-scoped observation extraction.

The Themes Prompt Contract owns prompt requirements.

Downstream layers consume the result of Themes, not Theme Input Boundary
directly.

---

# Forbidden Responsibilities

Theme Input Boundary never:

* constructs prompts
* defines prompt wording
* invokes LLMs
* extracts Themes
* performs observation clustering
* performs Topic Assignment
* generates intelligence
* performs business understanding
* generates Structured Intelligence
* creates Company Knowledge
* generates Business Signals
* performs business interpretation
* performs investor reasoning
* summarizes evidence
* infers business meaning
* reconstructs grounding
* creates evidence identities

Any responsibility in this list belongs to another platform layer or contract.

# Theme Input Boundary Content

The Theme Input Boundary builder returns:

```typescript
BuilderResult<ThemeInputBoundaryContent>
```

```typescript
type ThemeInputBoundaryContent = {
  grounding_artifact_id: string;
  filing_id: string;
  filing_hash: string;
  input_version: string;
  visible_evidence: ThemeVisibleEvidenceEntry[];
  visible_section_hierarchy: ThemeVisibleSection[];
  permitted_metadata: ThemePermittedMetadata;
};

type ThemeVisibleEvidenceEntry = {
  evidence_ref: string;
  section_name: string;
  paragraph_index: number;
  paragraph_text: string;
};

type ThemeVisibleSection = {
  section_name: string;
  evidence_refs: string[];
};

type ThemePermittedMetadata = {
  source_grounding_artifact_id: string;
  visible_evidence_count: number;
  visible_section_names: string[];
};
```

`ThemeInputBoundaryContent` is the canonical persisted source for Themes
input visibility.

It is not a prompt.

It is not a system prompt.

It is not a user prompt.

It is not Theme output.

It is not a Topic.

It is not business understanding.

It is not investor interpretation.

---

# Theme Input Contract

The canonical Theme Input contract contains only deterministic data.

It includes:

* filing identity
* ordered visible evidence
* evidence references
* permitted metadata
* visible section hierarchy
* input version

It must not include:

* prompts
* prompt instructions
* system prompts
* user prompts
* Theme output
* observations
* Topics
* business interpretation
* investor reasoning
* model identifiers
* LLM output

The Theme Input package may include paragraph text only as deterministic
context attached to visible `evidence_ref` values.

Paragraph text must not become a replacement evidence identity.

---

# Visibility Rules

Visibility rules define which deterministic grounding fields are exposed to
the Themes layer.

Theme Input Boundary may expose:

* `evidence_ref`
* `section_name`
* `paragraph_index`
* `paragraph_text`
* permitted deterministic metadata

Theme Input Boundary must not expose:

* hidden grounding metadata
* non-visible evidence
* upstream artifacts
* raw filing content outside visible evidence entries
* alternate evidence catalogs
* chunk identifiers as evidence identities
* prompt templates
* prompt wording
* model configuration
* LLM output

Visibility filtering must be deterministic and replayable.

Hidden evidence must never become visible without changing the Theme Input
Boundary output.

---

# Single Visible Input Principle

Themes has exactly one LLM-visible evidence input:

```text
Theme Input Boundary Artifact
```

The Themes layer must not receive the same filing evidence through a second
representation.

Supplying both Theme Input Boundary output and direct upstream evidence
creates:

* competing source representations
* avoidable input duplication
* grounding ambiguity
* evidence selection drift
* opportunities to describe unexposed text
* weaker replay and audit reasoning

The single visible input rule removes that ambiguity.

---

# Builder Boundary

The Theme Input Boundary builder owns:

* input package construction
* visibility enforcement
* deterministic filtering
* validation
* artifact construction

The builder returns:

```typescript
BuilderResult<ThemeInputBoundaryContent>
```

The builder must never:

* invoke an LLM
* construct prompts
* define prompt wording
* define prompt variables
* summarize evidence
* infer business meaning
* extract Themes
* assign Topics
* reconstruct grounding
* create evidence identities
* persist artifacts directly
* assign artifact IDs
* assign artifact versions
* manage current pointers

The standard builder lifecycle, persistence sequence, lineage requirements,
and failure behavior are defined by the Builder Contract and Builder
Implementation Guide. This specification does not duplicate those contracts.

---

# Validation

Theme Input Boundary validates that the Theme Input package is complete,
deterministic, visible, ordered, and correctly scoped to the source Theme
Grounding Artifact.

Validation must verify:

* input completeness
* visibility consistency
* evidence ordering preserved
* reference integrity
* metadata consistency
* deterministic filtering
* replay consistency
* visible section hierarchy consistency
* filing identity consistency
* filing hash consistency
* every visible `evidence_ref` exists in the source Grounding Package
* no hidden evidence is exposed
* no non-visible evidence is referenced
* no prompt fields are present
* no Theme fields are present
* no Topic fields are present

Validation failures must stop artifact creation.

Validators must not silently add, remove, rewrite, repair, or replace visible
evidence entries.

Validation must not evaluate:

* Theme quality
* prompt quality
* LLM quality
* business quality
* investor quality
* model behavior

Those responsibilities belong to downstream layers or other contracts.

---

# Replayability

Theme Input Boundary is deterministic.

For identical Theme Grounding Artifact content and identical Theme Input
Boundary contract version:

```text
Identical Theme Grounding Artifact
      ↓
Identical Theme Input Boundary Artifact
```

Theme Input Boundary generation must produce:

* identical visible evidence
* identical visible section hierarchy
* identical permitted metadata
* identical input version
* identical Theme Input Boundary content

Replayability must not depend on:

* prompts
* providers
* models
* LLM output
* mutable external state
* downstream artifacts
* filesystem enumeration order
* execution concurrency

Theme Input Boundary generation must be deterministic and must not use an
LLM.

---

# Output Boundary

The output of Theme Input Boundary is consumed only by the Themes layer.

Theme Input Boundary must not communicate directly with:

* Topic Assignment
* Structured Intelligence
* Company Knowledge
* Business Signals
* Quarter Understanding
* Investor Intelligence

All downstream intelligence flows through Themes.

---

# Downstream Boundary

Themes consumes Theme Input Boundary.

Themes must never:

* redefine visible evidence
* bypass visibility rules
* reconstruct grounding
* access hidden evidence
* consume raw upstream artifacts
* replace the Theme Input package

Theme Input Boundary determines visibility.

Themes performs observation extraction.

Prompt construction and prompt compliance are governed by the Themes Prompt
Contract.

---

# Future Compatibility

Theme Input Boundary is filing-type aware but remains deterministic.

Future filing categories may introduce new canonical sections, including:

```text
10-K
transcript
investor_presentation
other approved filing categories
```

Each filing-type policy may define deterministic visibility expectations for
the Theme Input package.

Future filing types must continue using:

* canonical Theme Grounding input
* deterministic visibility filtering
* ordered visible evidence
* permitted metadata
* input versioning
* replayable input package construction

Adding a filing type must not change existing Theme Input Boundary outputs for
previously supported filing types.
