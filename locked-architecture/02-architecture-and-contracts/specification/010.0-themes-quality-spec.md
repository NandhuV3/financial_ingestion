# Themes Quality Specification

Version: 1.0
Status: LOCKED
Owner: Themes Quality Layer

## Layer Contract Summary

Inputs

* Evidence Identity Artifact

Outputs

* Themes Quality Artifact

Primary Consumer

* Theme Grounding Layer

Execution Type

* Deterministic

---

# Purpose

Themes Quality is the canonical structural readiness layer before Themes.

It answers:

```text
Is the Evidence Identity artifact structurally ready for Themes?
```

The Themes Quality layer owns:

* structural readiness evaluation
* deterministic quality validation
* execution readiness
* quality findings
* readiness decision
* deterministic quality metrics

It establishes whether the Evidence Identity artifact is structurally ready
for Theme Grounding and Themes Builder execution.

It carries forward validated canonical evidence required by Theme Grounding.

Themes Quality contains no intelligence.

It performs no LLM reasoning.

It performs no business understanding.

It performs no interpretation.

---

# Platform Object Classification

Themes Quality is a Platform Foundation Artifact.

Reason:

Themes Quality performs deterministic readiness evaluation.

It contains no business understanding.

It contains no LLM reasoning.

It enables downstream Themes execution by validating structural readiness of
canonical evidence and carrying forward validated canonical evidence required
by Theme Grounding, not by creating observations or intelligence.

Artifact Framework owns:

* artifact identity
* framework metadata
* framework lineage
* artifact versioning
* persistence
* current pointer management
* archive and history
* framework-level artifact hashes

The Themes Quality content contract does not own those mechanics.

Themes Quality metrics and findings are content-level readiness fields owned
by this specification.

Validated evidence carried by Themes Quality is content-level evidence
readiness output. It does not create evidence identity and does not replace the
Evidence Identity Artifact.

# Input Boundary

The Themes Quality layer consumes only:

* Evidence Identity Artifact

It must never consume:

* Filing Artifact
* Extraction output
* Normalization output
* raw SEC filings

Evidence Identity is the only approved upstream input.

This preserves deterministic layer ownership and prevents upstream boundary
leakage.

---

# Output Principle

Themes Quality produces exactly one readiness assessment for one Evidence
Identity artifact.

Theme Grounding must consume only approved Themes Quality output.

Theme Grounding must never bypass Themes Quality.

Theme Grounding must never reopen Evidence Identity.

No downstream layer may construct an alternative canonical readiness
assessment for Themes execution.

# Themes Execution Readiness Content

The Themes Quality builder returns:

```typescript
BuilderResult<ThemesExecutionReadinessContent>
```

```typescript
type ThemesExecutionReadinessContent = {
  evidence_identity_artifact_id: string;
  filing_id: string;
  filing_hash: string;
  readiness_status: "ready" | "not_ready";
  validated_evidence: ThemesReadinessEvidenceEntry[];
  validated_section_hierarchy: ThemesReadinessSection[];
  findings: ThemesQualityFinding[];
  metrics: ThemesQualityMetrics;
};

type ThemesReadinessEvidenceEntry = {
  evidence_ref: string;
  evidence_hash: string;
  filing_id: string;
  section_name: string;
  paragraph_index: number;
  paragraph_text: string;
};

type ThemesReadinessSection = {
  section_name: string;
  evidence_refs: string[];
};

type ThemesQualityFinding = {
  finding_id: string;
  severity: "blocking" | "warning" | "info";
  code: string;
  message: string;
  evidence_ref?: string;
};

type ThemesQualityMetrics = {
  evidence_entry_count: number;
  section_count: number;
  section_distribution: Record<string, number>;
  duplicate_reference_count: number;
  orphan_reference_count: number;
  invalid_hash_count: number;
  ordering_issue_count: number;
};
```

`ThemesExecutionReadinessContent` is the canonical persisted source for Themes
execution readiness.

It carries forward validated canonical evidence for Theme Grounding.

Validated evidence entries are copied from the Evidence Identity Artifact only
after deterministic structural validation.

Themes Quality must not create, rewrite, rehash, renumber, reorder, or
reinterpret evidence.

It is not a Theme.

It is not an evidence identity.

It is not a Topic.

It is not business understanding.

It is not investor interpretation.

---

# Validated Evidence Carry-Forward

Themes Quality remains a validation checkpoint.

It may carry forward canonical evidence only after validating that the Evidence
Identity Artifact is structurally ready for downstream Theme execution.

For a `ready` result:

* `validated_evidence` contains every canonical evidence entry approved for
  Theme Grounding
* `validated_section_hierarchy` preserves canonical section ordering and
  evidence reference grouping
* evidence ordering is identical to the Evidence Identity source
* evidence references are unchanged
* evidence hashes are unchanged
* paragraph text is unchanged

For a `not_ready` result:

* Theme Grounding must not execute
* no downstream layer may use readiness output to bypass readiness failure
* any carried evidence must still reconcile with Evidence Identity

Validated evidence carry-forward is not evidence identity ownership.

Evidence Identity remains the canonical evidence owner.

Themes Quality only validates and carries forward the canonical evidence needed
by Theme Grounding.

---

# Readiness Model

Themes Quality determines whether Evidence Identity is structurally ready for
Theme Grounding and Themes Builder execution.

Readiness is a deterministic decision derived from the Evidence Identity
Artifact and governed readiness rules.

The readiness decision may be:

```text
ready
not_ready
```

`ready` means the Evidence Identity Artifact satisfies the structural
requirements for Themes execution.

`not_ready` means at least one blocking structural finding prevents Themes
execution.

A `not_ready` result prevents Themes execution.

It does not modify the Evidence Identity Artifact.

It does not repair structural defects.

It only reports deterministic readiness findings.

Readiness is not a judgment about:

* Theme quality
* prompt quality
* LLM quality
* model behavior
* business relevance
* management quality
* investor value

---

# Readiness Independence Principle

Themes Quality determines whether Themes execution may begin.

Themes Quality never influences which Themes are extracted.

The readiness decision and Theme extraction are completely independent
architectural responsibilities.

---

# Deterministic Readiness Principle

The readiness decision must depend only on deterministic rules.

It must never depend on:

* prompt quality
* LLM quality
* model behavior
* model output
* business interpretation
* downstream artifacts
* mutable external data
* hidden randomness

For identical Evidence Identity input and identical Themes Quality contract
version:

```text
Identical Evidence Identity
      ↓
Identical Themes Quality
```

Readiness metrics observe structural artifact characteristics.

They do not rewrite Evidence Identity.

They do not create Themes.

They do not alter downstream ownership.

# Structural Readiness Checks

Themes Quality evaluates structural readiness of the Evidence Identity
Artifact.

Required checks include:

* Evidence Identity completeness
* deterministic evidence ordering
* reference integrity
* evidence catalog consistency
* required structural fields
* replay consistency
* section distribution availability
* duplicate evidence reference absence
* orphan evidence reference absence
* evidence hash reconciliation
* filing identity consistency
* filing hash consistency
* validated evidence completeness
* validated evidence ordering
* validated section hierarchy consistency

These checks determine whether Themes can safely consume the canonical
evidence source.

They also determine whether canonical evidence may be carried forward to Theme
Grounding.

They do not evaluate what Themes should say.

---

# Quality Findings

Quality findings describe structural readiness issues.

Findings must distinguish:

* invalid artifact structure
* invalid evidence reference
* orphan evidence reference
* invalid evidence hash
* missing required field
* invalid ordering
* missing section coverage required for execution
* replay inconsistency

Findings must be deterministic and reproducible from the Evidence Identity
Artifact.

Findings may be classified as:

* `blocking`
* `warning`
* `info`

Only blocking findings make the artifact `not_ready`.

Warnings and informational findings remain observable unless a locked
readiness rule defines them as blocking.

Quality findings must not:

* invent missing Themes
* rewrite evidence
* create evidence identities
* create Topics
* infer business meaning
* infer investor relevance
* compare with another period
* alter evidence lineage

---

# Quality Metrics

Themes Quality metrics are deterministic readiness and observability fields.

They describe Evidence Identity structure.

They do not automatically determine business quality.

Required metric semantics:

## `evidence_entry_count`

The number of canonical evidence entries in the Evidence Identity Artifact.

## `section_count`

The number of canonical sections represented in the Evidence Identity
Artifact.

## `section_distribution`

The number of evidence entries in each canonical section.

Section distribution is structural. It is not a judgment about filing
importance or business relevance.

## `duplicate_reference_count`

The number of duplicate `evidence_ref` values detected.

Duplicate references are structural defects.

## `orphan_reference_count`

The number of evidence references that do not reconcile with a catalog entry.

Orphan references are structural defects.

## `invalid_hash_count`

The number of evidence entries whose `evidence_hash` does not reconcile with
the normalized paragraph text.

Invalid hashes are structural defects.

## `ordering_issue_count`

The number of detected violations of deterministic evidence ordering.

Ordering issues are structural readiness findings.

Additional metrics may be added only when they remain deterministic,
structural, and within Themes Quality ownership.

No metric in this specification authorizes:

* Theme creation
* Theme deletion
* Theme rewriting
* confidence recalibration
* Topic creation
* business interpretation
* investor interpretation

# Validation

Themes Quality validates that its readiness assessment is complete,
deterministic, and correctly scoped to the source Evidence Identity Artifact.

Validation must verify:

* Evidence Identity completeness
* deterministic evidence ordering
* reference integrity
* evidence catalog consistency
* required structural fields
* replay consistency
* readiness status reconciles with findings
* blocking findings produce `not_ready`
* absence of blocking findings produces `ready`
* `ready` output carries every canonical evidence entry required by Theme
  Grounding
* carried evidence references reconcile with Evidence Identity
* carried evidence hashes reconcile with Evidence Identity
* carried paragraph text reconciles with Evidence Identity
* carried evidence ordering reconciles with Evidence Identity
* carried section hierarchy reconciles with carried evidence
* metrics reconcile with the Evidence Identity Artifact
* findings reconcile with deterministic readiness checks
* source filing identity is preserved
* source filing hash is preserved

Validation failures must stop artifact creation.

Validators must not silently remove, rewrite, repair, or replace invalid
readiness findings.

Validation must not evaluate:

* Theme quality
* business quality
* trust
* investor quality
* management quality
* prompt quality
* LLM quality
* model behavior

Those responsibilities belong to downstream layers or other contracts.

# Replayability

Themes Quality is deterministic.

For identical Evidence Identity Artifact content and identical Themes Quality
contract version:

```text
Identical Evidence Identity
      ↓
Identical Themes Quality
```

Themes Quality generation must produce:

* identical readiness status
* identical validated evidence
* identical validated section hierarchy
* identical findings
* identical metrics
* identical Themes Execution Readiness content

Replayability must not depend on:

* prompts
* models
* providers
* LLM output
* downstream artifacts
* mutable external data
* filesystem enumeration order
* execution concurrency

Themes Quality generation must be deterministic and must not use an LLM.

Theme Grounding begins where Themes Quality ends.

# Future Compatibility

Themes Quality readiness rules are filing-type aware but remain deterministic.

Future filing categories may introduce new canonical sections, including:

```text
10-K
transcript
investor_presentation
other approved filing categories
```

Each filing-type policy may define structural readiness expectations for the
Evidence Identity Artifact.

Future filing types must continue using:

* deterministic readiness evaluation
* canonical Evidence Identity input
* structural findings
* readiness status
* validated canonical evidence carry-forward
* replayable metrics

Adding a filing type must not change existing Themes Quality outputs for
previously supported filing types.
