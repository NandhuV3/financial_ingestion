# Architecture Cleanup Report

Generated: 2026-06-10

Scope: static repository audit only. No code was modified as part of this report.

## Executive Summary

The repository is mostly organized around clear domain slices, but several cleanup candidates have accumulated from iterative phase work:

- Generated build outputs are present in the repository tree.
- One empty source folder exists.
- One legacy identity module appears unreferenced.
- Business Signal builder design documentation exists in two locations.
- Some tests reference a stale Company Knowledge type path.
- Repository implementations intentionally repeat the same file persistence pattern.
- Builder implementations repeat lineage, hashing, normalization, and deduplication helpers.

Not every item below should be deleted immediately. Some files are CLI entrypoints, future orchestration seams, persisted intelligence artifacts, or fixtures. Cleanup should preserve artifact auditability and the established builder/repository/command ownership boundaries.

## 1. Unused Folders

### Confirmed Empty Folder

- `src/partner-api/`

This directory is empty. The active Fastify API implementation lives under `src/api/`.

Recommendation: remove the empty folder unless it is being reserved for a near-term package migration.

### Generated Output Folders

- `dist/`
- `apps/partner-web/dist/`

These look like build outputs, not source architecture. If they are tracked, they should be removed from source control and regenerated by the build pipeline.

Recommendation: keep generated output out of the architecture source tree unless intentionally publishing static artifacts from this repository.

## 2. Unused Files

### Likely Dead Legacy Module

- `src/company-identity/legacy/identity-signals.ts`

No active references were found during the audit. The current identity architecture has moved toward evidence and enrichment, so this legacy keyword-oriented module appears obsolete.

Recommendation: delete after confirming no external/manual script imports it.

### Generated Metrics Artifact In Source

- `src/analysis/pipeline-metrics.json`

This appears to be generated output stored under `src/`. Generated analysis artifacts should generally live under `data/`, `reports/`, or `warehouse/`, not source code.

Recommendation: move future generated metrics out of `src/`, or document why this file is source-owned.

### Test Fixture Data

- `data/TESTC/`

`TESTC` is referenced by `tests/comparison.test.ts`, so it is not unused. It is test fixture data.

Recommendation: keep it, but consider documenting it as fixture data or moving it under a dedicated test fixture path in a later cleanup.

## 3. Duplicate Contracts

### Duplicate Business Signal Builder Design Document

Two Business Signal builder design documents exist:

- `src/business-signal-intelligence/business-signal-builder-design.md`
- `src/business-signal-intelligence/docs/business-signal-builder-design.md`

This is the clearest duplicate contract/design artifact. The newer convention appears to be `src/<domain>/docs/`.

Recommendation: keep `src/business-signal-intelligence/docs/business-signal-builder-design.md` as canonical and remove or redirect the root-level duplicate after confirming content parity.

### Contract Location Drift

Several domains now use `src/<domain>/docs/`:

- `src/company-knowledge/docs/`
- `src/business-signal-intelligence/docs/`
- `src/quarter-understanding-intelligence/docs/`

Earlier phases also created architecture documents under root `docs/`.

This is not necessarily wrong: product/platform documents belong in root `docs/`, while domain contracts can live beside domain code. The important cleanup is to avoid duplicate copies of the same contract in both places.

Recommendation: formalize the convention:

- Root `docs/`: product, architecture, frontend, research, cross-domain strategy.
- `src/<domain>/docs/`: domain-owned contracts for builders, schemas, repositories, storage, prompts, and ownership.

## 6. Duplicate Repositories

The following repositories repeat the same storage mechanics:

- `src/company-knowledge/company-knowledge.repository.ts`
- `src/business-signal-intelligence/business-signal.repository.ts`
- `src/quarter-understanding-intelligence/quarter-understanding.repository.ts`

Repeated behavior includes:

- Warehouse path construction
- `current.json` loading
- `archive/{version}.json` loading
- Version discovery
- Archive-first writes
- Atomic `current.json` replacement through temp file + rename
- Missing-file null handling
- Invalid JSON error handling

This duplication is understandable because each repository was implemented after separate storage contracts were stabilized. It is not functionally wrong.

Recommendation: once the repository contracts stop changing, extract a small internal file-artifact repository helper. Keep domain repositories as thin wrappers so path ownership and type ownership remain clear.

Do not introduce a generic persistence framework. A small reusable helper for archive/current semantics is enough.

## 7. Duplicate Builders

The current builders are domain-specific and should remain separate:

- `src/company-knowledge/build-company-knowledge.ts`
- `src/business-signal-intelligence/build-business-signals.ts`
- `src/quarter-understanding-intelligence/build-quarter-understanding.ts`

However, they repeat low-level helper concerns:

- Stable hashing
- Timestamp normalization before hashing
- String/array normalization
- Deduplication
- Lineage merging
- Stable sorting
- Empty input safety

This is not duplicate business logic. It is duplicate infrastructure logic.

Recommendation: after Quarter Understanding command/repository work stabilizes, consider shared helpers under something like:

```text
src/shared/artifacts/
  artifact-hashing.ts
  artifact-lineage.ts
  artifact-normalization.ts
```

Keep field assembly and domain decisions inside each builder.

## Cleanup Risk Notes

- Do not delete intelligence artifacts under `data/` or `warehouse/` without deciding whether they are product evidence, examples, or fixtures.
- Do not collapse domain repositories into one generic repository abstraction too early. The domain-specific interfaces are useful and keep ownership clear.
- Do not centralize business assembly logic. Only centralize mechanical helpers like hashing, lineage normalization, and archive/current file IO.
- Do not treat CLI entrypoints as dead code solely because they are not imported.

## Conclusion

The highest-value cleanup items are documentation duplication, stale test import paths, empty/generated folders, and one legacy identity module. The repository also has intentional repetition across newly stabilized artifact repositories and builders. That repetition is acceptable for now, but small shared helpers can reduce maintenance cost once the contracts stop moving.
